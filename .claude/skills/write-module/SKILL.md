# Write a module

A module of devkit is a [flake-parts](https://flake.parts) module that gives a repository checks, setups, generated files or a formatter.
This skill gives the rules that no check of devkit enforces.
The flake, the tests and the workflow already enforce the rest, as the last section says.

## Name it

A module is named after the kind of files it handles, never after a tool: `shell` runs ShellCheck and shfmt, `nix` runs nixfmt.
A check of the module keeps its tool's name, such as `check-nixfmt`, so that a failure names the tool.
A module that handles no kind of files is named after what it gives: `checks`, `commands`, `files`, `setups`, `commits`.

## Lay it out

- `src/modules/<name>/default.nix` is the module, and the directory holds every file that the module reads: templates (`*.in`), scripts and configurations.
- `tests/modules/<name>/` holds only the module's test files.
  A helper of one module's tests goes in `tests/libs/<name>.nix`, and a helper of several modules' tests in `tests/libs/`.
- `skills/devkit-<name>/SKILL.md` is the module's skill.

## Build it on the other modules

- The module imports, by their relative paths, the modules whose options it sets, such as `../checks`.
- It reads devkit's shared values from `../../lib.nix`, never from a module.
- A module reads only its own files and those of the modules that it imports, such as `../commands/built.nix`, never those of a module that builds on it.
- `devkit.checks.<name>` defines each check.
  A command line with its `packages` suits a short check; a longer one is a template built with `mkCommand`.
- `devkit.files.<path>` generates each configuration file that the repository commits.
- `devkit.setups.<name>` defines each setup that writes files outside `devkit.files`.

The skills of these modules, `devkit-checks`, `devkit-commands`, `devkit-files` and `devkit-setups`, describe their options.

## Use the shared values

A tool that has a setting for a value of `src/lib.nix`, such as its line length or its indentation, gets the shared value explicitly, even when it equals the tool's default.
A file or section that wants no such limit sets none, as `.editorconfig` does for Markdown.
A new shared value is a constant of `src/lib.nix`, with the reason that every repository needs it, never an option.

## Assume the other modules

A repository that has files of a kind uses devkit's module for it, and a repository that has none does not import it.
A module may therefore leave a kind of files to the module that handles it, as `.editorconfig` leaves the line length of YAML files to the `yaml` module.

## Give no option without a need

A module offers no option, override or guard that no repository needs today.

## Test it

Each test file of `tests/modules/<name>/` is named after what it tests, such as `check.nix`, `setup.nix` or `formatter.nix`.
It returns an attribute set of cases, each named after what it shows.
The `tests/default.nix` loader names each case `test-<name>-<file>-<case>`.

- A case builds a repository with the `repository` helper of `tests/libs/repository.nix` and runs an app of the module.
  It takes the app from `consumer`, given the module and only the configuration that the case needs, so that nothing else changes what the case tests.
- Each check has a case that passes and a case for each way it fails, with the status and the output that the failure must print.
- Each shared value that the module passes to a tool has a case that shows the tool applies it.
- A case that shows how a tool behaves says why the module relies on that behavior.

## Document it

The module's skill describes the module as a black box: what to import, its apps, options and generated files, and how to set it up.
It never describes the modules that it builds on; it says only which ones it uses, as the `devkit-yaml` skill does for the `files` module.
It links each tool rather than describing what the tool does or prints, and it points to a generated file rather than restating its rules or values.

The skill's `description` says what the module does, names devkit's module, and ends with `Use this when …`:

- a module that checks a kind of files: "Check a repository's YAML files with yamllint, using a configuration generated by devkit's `yaml` module. Use this when setting up the YAML check, or when it fails.";
- a module for writing one's own checks, setups, commands or files: "Implement a repository-specific … with devkit's `…` module. Use this when a repository needs … that none of devkit's modules provides."

A module that checks a kind of files has a `Set it up` section with numbered steps:

1. Import `inputs.devkit.flakeModules.<name>`, as the `devkit` skill shows.
2. If the module generates files: run `nix run .#setup-files`, and commit the files.
3. Run each of its checks.

## Use it in devkit

devkit's `flake.nix` imports every module whose kind of files devkit has, in alphabetical order, and commits the files they generate.

## What devkit already enforces

- `flakeModules` has one module for each directory of `src/modules`.
- The `alone` test imports each module alone and builds every check, app, shell and formatter that it gives, so that a missing import fails.
- Each command gets a `lint-<name>` flake check with ShellCheck and shfmt, built by the module's `test-<name>` check.
- The loader refuses a directory of `tests/modules` that has no module.
- The workflow runs a job for each `check-<name>` app and each `test-<name>` check, so that a new module needs no change in `.github/workflows`.

Before pushing, run `nix run .#check` and `nix flake check`.
